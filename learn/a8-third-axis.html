The Third Axis

Every unit so far has read a flat grid — rows going down, features going across. That is what a screen is, and it is only ever two axes.

Most real records are not flat. A video has height, width and time. A scan has three spatial axes. A trial-based experiment has trials, steps and channels. The moment a third axis appears, there is no longer one reading.

This unit is about what to do then, and about how easily the obvious answer is wrong.

A field, and a decision nobody records

The EEG carried through units A3, A4, A6 and B3 is stored as 800 × 4 — 800 readings, one after another, from 4 electrodes. Flat.

But readings usually come in runs. So it can equally be read as 100 trials × 8 steps × 4 electrodes, and every unit below does exactly that.

Nothing in the file says that is true. The trial length was chosen — here, so the numbers divide neatly. A different choice gives a different field, and the instrument will answer just as confidently either way.

That decision is the subject here. Where the third axis comes from is settled outside the data, and it usually goes unrecorded, because it is made by whoever wrote the loading code and it looks like plumbing.

One field, many screens

A screen takes two axes. A field has three. So the first question is which two — and each answer gives a different number of screens, of a different size:

screen made from axeshow manyeach
1 and 21008 × 4

0 and 28100 × 4

These are not three views of one thing. They are three genuinely different objects. Reading one trial as a picture of steps against electrodes asks how the electrodes move together within a run. Reading one electrode as trials against steps asks whether the runs resemble each other.

Both are reasonable questions. Neither is the question, and the data does not prefer one.

Seven answers to one question

Take the simplest read in the whole curriculum — the fill fraction, φ (the Greek letter phi, said FYE), which unit A2 used to say how much of a screen a signal occupies. Ask it of this one field, seven ways:

The principled reductions land between 0.3027 and 0.7192. The last row — a plain reshape back to the shape the file was stored in — reads 0.9490, well above all of them.

Every number in that column is the same function, applied to the same bytes. The only thing that changed is how three axes were folded into two.

Two reductions, and which read takes which

The library does not leave this to the caller's instinct. It provides exactly two ways down to a screen, and states which reads each one is correct for:

reductionwhat it doescorrect for
over planeskeep each plane whole, read every one, combine the answers reads about features — how much of a plane is occupied, how concentrated it is
poolflatten every other axis into the feature axis, so each off-axis position becomes another sample of the same ordered process reads about the ordered axis — decay, rates, how fast things fade

The reasoning is short. A feature read asks about structure within a plane, so the plane must stay intact. An ordered read asks how a quantity evolves along one axis, and every other position is another independent witness of that same evolution — so pooling them gathers information.

The module's own words: getting these backwards changes the answer, and a naive flatten “destroys the within-plane correlation and can silently invert a read”. The module's word is invert, and it means what it says: the answer can come back pointing the other way.

Why the plain reshape is the dangerous one

Look at those last two rows again, because they do not fail in the same way.

bare reshapeφwhat happened
flatten to 100 × 320.302704the same array as pool on ordered axis 0 — the file's own ordering
flatten to 800 × 40.949016no principled reduction gives this

One of them is a correct reduction, element for element: the file already stores the numbers in that order, so flattening to that shape and pooling that axis produce the same array. The other has a shape no pooling produces — pooling the electrode axis gives 4 × 800, and the reshape gives 800 × 4, transposed.

So a bare reshape is not reliably wrong. It is unpredictably right, which is worse: it works, you stop checking, and then the field's shape changes by one axis and it silently stops working with no error and no visible difference in the code.

A method that is correct on the cases you happened to try is indistinguishable, from the inside, from a method that is correct.

The fold is a choice as well

Everything so far varies the reduction and holds the field fixed at 100 × 8 × 4. But nothing in the file says that fold is the right one. The record is 3,200 numbers; 800 rows divide several ways, and each one is as legal as the one this unit picked. So: the same reductions, every legal fold, nothing else changed.

Reading down any column: choosing the fold moves the answer by up to 0.3431. Reading across the earlier table, choosing the reduction moves it by 0.4165. The two choices cost about the same, and the reader makes both.

Neither is recorded in the number that comes out. A figure like “0.5009” is the answer to this reduction of this fold, and a reader handed the figure alone cannot recover either.

Which is why the honest form of a three-axis read is not a number but a number with its two choices attached. Unit D8 reaches the same place from the other end: there the question was which rows a filter kept, here it is which shape the rows were poured into, and both are decisions a reader makes and a figure forgets.

And it runs the other way

If a third axis makes a record harder to read, it also makes one richer — and a flat record can be given one deliberately.

Take each moment together with the few that follow it. That stack of short windows is a third axis, built out of the record's own history: 800 × 4 becomes 797 × 4 × 4, with the new axis being how far back.

Now all three can be read at once, giving one set of directions per axis:

directionsstrengths (largest first)
along time69.170 · 59.811 · 51.839 · 42.922
across electrodes77.812 · 64.555 · 55.914 · 47.519
across lags113.261 · 46.944 · 21.142 · 11.300

The whole record compresses into a core of 8 × 4 × 4 numbers plus those three sets of directions — and rebuilding from it recovers the original to 0.9608 of itself, returning to exactly its original 800 × 4.

Which is unit A1's idea — a few strong patterns carry most of a record — running in three directions at once.

The third axis is a decision, usually undocumented

A screen has two axes. Give it a record with three and something has to give — and what gives is the uniqueness of the answer.

  • The third axis is a decision, usually undocumented. This field's trial length was chosen so the numbers divided neatly. Nothing in the file mentions trials.
  • One read, seven reductions, values from 0.3027 to 0.7192. Same function, same bytes, different fold.
  • There are two correct reductions and they are for different questions — one keeps planes whole, one pools them — and the library says which is which.
  • A bare reshape is unpredictably right. Sometimes it matches a correct reduction exactly, by accident of memory layout.

The same dependence shows up wherever the instrument is pointed. Unit A7: the answer depends on what you call nothing. Unit A10: on how much record you have. Here: on how you fold the axes. The arithmetic is exact in every case, and the number carries the choice that produced it.
